# OYNA: контекст для будущего продолжения

Этот файл нужен, чтобы после переустановки Windows на Linux можно было быстро понять, что мы уже сделали, зачем мы это сделали, как запустить проект и что делать дальше.

## Идея продукта

OYNA — единое мобильное приложение для компьютерных клубов Казахстана.

Проблема: у многих клубов есть SENET, SmartShell, LANGAME или другая внутренняя система, но нет удобного мобильного приложения для игроков. Игроку приходится писать в WhatsApp/Instagram, звонить или приходить на место.

Решение: одно приложение, где игрок может найти клуб, посмотреть зоны и цены, выбрать время и ПК, отправить бронь, видеть статус и историю. Для клуба — простой веб-кабинет, где администратор подтверждает или отклоняет заявки.

## Почему начали с ручного пилота

Изначально думали сразу подключать SENET API. Но безопаснее не выдумывать несуществующие эндпоинты и не просить у клуба пароль владельца или кассира.

Поэтому первая версия сделана как пилот:

- игрок создает заявку на бронь;
- заявка получает статус `pending`;
- администратор клуба видит ее в кабинете;
- администратор вручную подтверждает или отклоняет бронь;
- позже можно подключить официальный API SENET/SmartShell/LANGAME, когда клуб или поставщик даст документацию, sandbox или partner access.

Это позволяет пойти к первому клубу уже с рабочей демонстрацией, не ломая их реальную систему.

## Что уже реализовано

Проект сделан как monorepo на `pnpm`.

Основные части:

- `apps/mobile` — мобильное приложение игрока на Expo / React Native.
- `apps/dashboard` — веб-кабинет клуба на Next.js.
- `apps/api` — backend API на NestJS.
- `packages/contracts` — общие TypeScript-типы и контракты между mobile, dashboard и API.
- `docs` — документы для пилота и интеграции.
- `scripts` — вспомогательные скрипты.

### Mobile app

Уже есть:

- список клубов;
- карточки клубов;
- экран клуба;
- выбор даты, времени, зоны и мест;
- проверка доступности мест;
- создание брони;
- экран успешной отправки заявки;
- вход по телефону;
- dev OTP-код `0000`;
- хранение сессии через `expo-secure-store`;
- история броней;
- отображение статусов;
- отмена будущей брони;
- logout.

### Dashboard

Уже есть:

- темный кабинет клуба;
- метрики и таблица броней;
- очередь заявок на подтверждение;
- кнопки подтверждения и отклонения;
- server action в Next.js, который обращается к API с admin key;
- fallback-данные, чтобы интерфейс не был пустым при локальной демонстрации.

### API

Уже есть:

- NestJS API;
- health endpoint;
- клубы и зоны;
- проверка доступности;
- создание брони;
- получение брони;
- список броней пользователя;
- список броней клуба для админа;
- отмена брони пользователем;
- смена статуса брони администратором;
- auth по телефону;
- HMAC-токен с `AUTH_SECRET`;
- dev OTP-код `0000`;
- `CLUB_ADMIN_KEY` для кабинета клуба;
- PostgreSQL через `pg`;
- автоматическое создание таблиц при наличии `DATABASE_URL`;
- in-memory режим, если базы нет;
- защита от двойного бронирования через транзакцию и advisory lock в PostgreSQL;
- тесты для auth, clubs и bookings.

### Интеграции

Создана заготовка под провайдеров клубных систем:

- `manual.provider.ts` — текущий ручной режим;
- `senet.provider.ts` — каркас для будущей SENET-интеграции;
- `club-provider.ts` — общий интерфейс провайдера.

Важно: SENET не подключен к выдуманным endpoint-ам. Для настоящей интеграции нужны официальные документы, тестовый доступ или partner/sandbox API.

## Как запустить после Linux

Понадобится:

- Node.js LTS;
- pnpm;
- Docker + Docker Compose;
- Git;
- Expo Go на телефоне или Android emulator.

Команды:

```bash
pnpm install
cp .env.example .env
pnpm db:up
pnpm dev:api
pnpm dev:dashboard
pnpm dev:mobile
```

Адреса по умолчанию:

- API: `http://localhost:4000/api`
- Dashboard: `http://localhost:3000`
- Mobile dev server: покажет Expo после `pnpm dev:mobile`

Для теста на реальном телефоне нужно в `.env` поставить `EXPO_PUBLIC_API_URL` на IP компьютера в локальной сети, например:

```env
EXPO_PUBLIC_API_URL=http://192.168.1.10:4000/api
```

Dev-код входа: `0000`.

## Что делать с первым клубом

Не начинать с просьбы “дайте пароль от SENET”. Правильный первый шаг:

1. Показать демо: игрок создает заявку, клуб подтверждает в dashboard.
2. Узнать, какая система у клуба: SENET, SmartShell, LANGAME или другая.
3. Собрать зоны, цены, список ПК, правила отмены, часы работы.
4. Попросить только безопасный технический доступ: sandbox, partner API, тестовый аккаунт или официальную документацию.
5. Первую неделю запустить “теневой режим”: OYNA создает заявки, админ сверяет вручную.
6. Потом дать несколько реальных мест под бронь без онлайн-оплаты.
7. Только после стабильных броней думать об оплате, депозитах и автоматической синхронизации.

## GitHub-план

Перед переустановкой Linux нужно сделать следующее:

1. Убедиться, что `.env` не попадает в репозиторий. Сейчас `.gitignore` уже содержит `.env` и `.env.local`.
2. Не заливать `node_modules`, `.pnpm-store`, `.next`, `.expo`, `dist`, `coverage`.
3. Создать новый GitHub repository, например `oyna-platform`.
4. Инициализировать или починить локальный git repository.
5. Сделать первый commit.
6. Добавить GitHub remote.
7. Выполнить push.
8. После установки Linux: `git clone`, `pnpm install`, `cp .env.example .env`, запуск.

## Если будущий Codex продолжает работу

Сначала прочитай этот файл, потом:

```bash
rg --files
Get-Content package.json
Get-Content .env.example
```

На Linux вместо `Get-Content` используй:

```bash
cat package.json
cat .env.example
```

Не подключай SENET “наугад”. Нужны официальные endpoint-ы, формат авторизации, webhooks, rate limits и правила создания/отмены броней.

Приоритет продукта сейчас — не идеальная архитектура, а первый работающий пилот с реальным клубом. Нам нужно доказать, что клубам удобно принимать брони через OYNA, а игрокам удобно бронировать ПК без звонков и переписок.
