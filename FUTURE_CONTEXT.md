# OYNA: контекст для будущего продолжения

Этот файл нужен, чтобы через месяц или через год можно было быстро понять, что мы уже сделали,
зачем мы это сделали, как запустить проект и что делать дальше.

Переезд с Windows на Linux состоялся: проект лежит в GitHub (`AltynbekBlessRnG/oyna-platform`),
клонируется и запускается на Linux, зависимости ставятся через `pnpm`.

## Идея продукта

OYNA — единое мобильное приложение для компьютерных клубов Казахстана.

Проблема: у многих клубов есть SENET, SmartShell, LANGAME или другая внутренняя система, но нет удобного мобильного приложения для игроков. Игроку приходится писать в WhatsApp/Instagram, звонить или приходить на место.

Решение: одно приложение, где игрок может найти клуб, посмотреть зоны и цены, выбрать время и ПК, отправить бронь, видеть статус и историю. Для клуба — простой веб-кабинет, где администратор подтверждает или отклоняет заявки.

## Почему начали с ручного пилота

Изначально думали сразу подключать SENET API. Но безопаснее не выдумывать несуществующие эндпоинты и не просить у клуба пароль владельца или кассира.

Поэтому первая версия сделана как пилот:

- игрок создаёт заявку на бронь;
- заявка получает статус `pending`;
- администратор клуба видит её в кабинете;
- администратор вручную подтверждает или отклоняет бронь;
- игрок сразу получает уведомление о решении;
- позже можно подключить официальный API SENET/SmartShell/LANGAME, когда клуб или поставщик даст документацию, sandbox или partner access.

Это позволяет пойти к первому клубу уже с рабочей демонстрацией, не ломая их реальную систему.

## Что уже реализовано

Проект сделан как monorepo на `pnpm`.

Основные части:

- `apps/mobile` — мобильное приложение игрока на Expo / React Native.
- `apps/dashboard` — веб-кабинет клуба на Next.js.
- `apps/api` — backend API на NestJS.
- `packages/contracts` — общие TypeScript-типы и контракты между mobile, dashboard и API.
- `docs` — документы для пилота и интеграции.
- `scripts` — вспомогательные скрипты.

### Mobile app

Уже есть:

- список клубов, карточки, экран клуба;
- выбор даты, времени, зоны и мест, проверка доступности;
- создание брони и экран успешной отправки;
- вход по телефону, dev OTP-код `0000`, хранение сессии через `expo-secure-store`;
- история броней, статусы, отмена будущей брони, logout;
- социальные экраны: сообщество, чаты, турниры, профиль;
- центр уведомлений и регистрация push-токена Expo после входа.

### Dashboard

Уже есть:

- тёмный кабинет клуба, метрики и таблица броней;
- метрики считаются по реальным броням клуба, а не по заглушкам;
- очередь заявок с подтверждением и отклонением;
- вход администратора клуба по телефону (`/login`), сессия в httpOnly-cookie;
- страница настроек клуба (`/settings`): название, адрес, город, статус, телефон, часы, теги, оборудование;
- редактор зон: добавление, удаление, цена за час и количество мест;
- fallback-данные, чтобы интерфейс не был пустым, когда API не запущен.

### API

Уже есть:

- NestJS API, health endpoint;
- клубы и зоны в PostgreSQL, каталог правится через кабинет и seed;
- проверка доступности, создание брони, получение и список броней;
- отмена брони пользователем, смена статуса администратором клуба;
- уведомление игроку при подтверждении, отклонении и завершении брони — запись в центре уведомлений плюс Expo push;
- auth по телефону, HMAC-токен с `AUTH_SECRET`, dev OTP-код `0000`;
- роли: `platform_admin`, `club_admin` с записью в `club_memberships`, запасной `CLUB_ADMIN_KEY`;
- PostgreSQL через `pg`, автоматическое создание таблиц при наличии `DATABASE_URL`;
- in-memory режим, если базы нет;
- защита от двойного бронирования через транзакцию и advisory lock;
- защита зоны с будущими бронями от удаления и уменьшения числа мест;
- социальные модули: чаты, профили, турниры, уведомления;
- 21 тест: auth, clubs, club access, bookings, chat, tournaments.

### Права доступа

Раньше весь кабинет открывался одним общим `CLUB_ADMIN_KEY`. Теперь:

- `platform_admin` — владелец платформы: видит все клубы, выдаёт доступы;
- `club_admin` + строка в `club_memberships` — управляет только своим клубом;
- `CLUB_ADMIN_KEY` — запасной ключ уровня платформы для демонстраций. В production работает,
  только если задан явно; в dev по умолчанию `pilot-admin`.

Все административные маршруты содержат `:clubId`, и API проверяет принадлежность клуба на каждом запросе.

### Интеграции

Заготовка под провайдеров клубных систем: `manual.provider.ts` (текущий ручной режим),
`senet.provider.ts` (каркас), `club-provider.ts` (общий интерфейс).

Важно: SENET не подключён к выдуманным endpoint-ам. Для настоящей интеграции нужны официальные документы, тестовый доступ или partner/sandbox API.

## Боевой стенд на Render

- API: `https://oyna-api.onrender.com` (сервис `oyna-api`, регион Frankfurt, план free).
- Кабинет клуба: `https://oyna-cabinet.onrender.com` (сервис `oyna-cabinet`, Frankfurt, free),
  переменная `API_URL` указывает на API. `CLUB_ADMIN_KEY` там намеренно не задан:
  без него кабинет не пускает анонимного посетителя и требует вход по телефону.
- База: `oyna-postgres`, PostgreSQL 18, Frankfurt, план free.
- Деплой автоматический из ветки `main` репозитория `oyna-platform`.
- Секреты (`AUTH_SECRET`, `CLUB_ADMIN_KEY`) заданы в Environment сервиса, в репозитории их нет.
- `DATABASE_URL` подключён через Render «Add from database» → Internal Database URL.

Команда сборки — без `corepack`, он падает на read-only `/usr/bin/pnpm`:

```
npx --yes pnpm@11.9.0 install --frozen-lockfile && npx --yes pnpm@11.9.0 --filter @oyna/contracts build && npx --yes pnpm@11.9.0 --filter @oyna/api build
```

Права администратора клуба выдаются по номеру телефона тем же ключом:

```bash
curl -X POST -H "x-club-admin-key: <ключ>" -H 'Content-Type: application/json' \
  -d '{"phone":"+7...","name":"Администратор"}' \
  https://oyna-api.onrender.com/api/admin/clubs/vertex-arena/members
```

Каталог клубов заливается без доступа к базе:

```bash
curl -X POST -H "x-club-admin-key: <ключ>" -H 'Content-Type: application/json' \
  -d '{}' https://oyna-api.onrender.com/api/admin/catalog
```

С телом `{"catalog": [...]}` загружается свой каталог, без тела — демонстрационный.

Ограничения бесплатного плана: **база удаляется 22 сентября 2026**, сервис засыпает
без трафика и просыпается около 30 секунд. В production код входа не возвращается в ответе
API и виден только в логах Render — до подключения SMS реальный игрок войти не сможет.

## Как запустить

Понадобится:

- Node.js LTS (проверено на Node 26);
- pnpm (`npm i -g pnpm`, если его нет в PATH);
- PostgreSQL: Docker Compose (`pnpm db:up`) либо `./scripts/local-postgres.sh install` без root;
- Git;
- Expo Go на телефоне или Android emulator.

Команды:

```bash
pnpm install
cp .env.example .env
pnpm db:up
pnpm db:seed
pnpm dev:api
pnpm dev:dashboard
pnpm dev:mobile
```

Адреса по умолчанию:

- API: `http://localhost:4000/api`
- Dashboard: `http://localhost:3000`
- Mobile dev server: покажет Expo после `pnpm dev:mobile`

Для теста на реальном телефоне нужно в `.env` поставить `EXPO_PUBLIC_API_URL` на IP компьютера в локальной сети, например:

```env
EXPO_PUBLIC_API_URL=http://192.168.1.10:4000/api
```

Dev-код входа: `0000`.

## Как завести реальный клуб

1. Скопировать `apps/api/clubs/example-club.json` и заполнить данными клуба.
2. `pnpm db:seed -- --file=./clubs/<клуб>.json` — путь считается от `apps/api`.
3. `pnpm db:seed -- --club=<id> --admin-phone=+7...` — выдать администратору доступ.
4. Администратор входит в кабинет на `/login` по своему номеру и правит клуб на `/settings`.

Seed идемпотентен: повторный запуск обновляет клубы и зоны, ничего не удаляя.

  в доступе к кабинету, подтверждение клубом, уведомление игроку — 11 из 11;
- кабинет проверен против живого API: обзор, настройки и вход отдают реальные данные клуба;
- SQL схемы, seed и административных запросов проверен на движке PostgreSQL 17 через PGlite,
  включая идемпотентность схемы и расчёт свободных мест.

Что не проверено:

- PostgreSQL именно в Docker: Docker на машине не установлен, а пароль sudo неизвестен,
  поэтому база поднята без root через `./scripts/local-postgres.sh`
  (настоящий PostgreSQL 18.4 в `~/.local/share/oyna`);
- реальное подключение SENET/SmartShell/LANGAME;
- push на настоящем телефоне: в Expo Go с SDK 53 remote push недоступны, нужен dev-билд
  и `extra.eas.projectId` в `app.json`;
- тест на настоящем Android-телефоне в клубе;
- публикация в App Store / Google Play.

## Что делать с первым клубом

Не начинать с просьбы “дайте пароль от SENET”. Правильный первый шаг:

1. Показать демо: игрок создаёт заявку, клуб подтверждает в dashboard, игрок получает уведомление.
2. Узнать, какая система у клуба: SENET, SmartShell, LANGAME или другая.
3. Собрать зоны, цены, список ПК, правила отмены, часы работы, телефон администратора.
4. Завести клуб через seed и выдать администратору доступ по его номеру.
5. Попросить только безопасный технический доступ: sandbox, partner API, тестовый аккаунт или официальную документацию.
6. Первую неделю запустить “теневой режим”: OYNA создаёт заявки, админ сверяет вручную.
7. Потом дать несколько реальных мест под бронь без онлайн-оплаты.
8. Только после стабильных броней думать об оплате, депозитах и автоматической синхронизации.

## Если будущий агент продолжает работу

Сначала прочитай этот файл, потом:

```bash
cat package.json
cat .env.example
pnpm install
pnpm test
pnpm typecheck
```

Не подключай SENET “наугад”. Нужны официальные endpoint-ы, формат авторизации, webhooks, rate limits и правила создания/отмены броней.

Приоритет продукта сейчас — не идеальная архитектура, а первый работающий пилот с реальным клубом. Нам нужно доказать, что клубам удобно принимать брони через OYNA, а игрокам удобно бронировать ПК без звонков и переписок.
