# OYNA: контекст для будущего продолжения

Этот файл нужен, чтобы через месяц или через год можно было быстро понять, что мы уже сделали,
зачем мы это сделали, как запустить проект и что делать дальше.

Репозиторий: GitHub `AltynbekBlessRnG/oyna-platform`.

## Идея продукта

OYNA — единое мобильное приложение для компьютерных клубов Казахстана.

Проблема: у многих клубов есть SENET, SmartShell, LANGAME или другая внутренняя система, но нет удобного мобильного приложения для игроков. Игроку приходится писать в WhatsApp/Instagram, звонить или приходить на место.

Решение: одно приложение, где игрок может найти клуб, посмотреть зоны и цены, выбрать время и ПК, отправить бронь, видеть статус и историю. Для клуба — простой веб-кабинет, где администратор подтверждает или отклоняет заявки.

## Почему начали с ручного пилота

Изначально думали сразу подключать SENET API. Но безопаснее не выдумывать несуществующие эндпоинты и не просить у клуба пароль владельца или кассира.

Поэтому первая версия сделана как пилот:

- игрок создаёт заявку на бронь;
- заявка получает статус `pending`;
- администратор клуба видит её в кабинете;
- администратор вручную подтверждает или отклоняет бронь;
- игрок сразу получает уведомление о решении;
- позже можно подключить официальный API SENET/SmartShell/LANGAME, когда клуб или поставщик даст документацию, sandbox или partner access.

Это позволяет пойти к первому клубу уже с рабочей демонстрацией, не ломая их реальную систему.

## Что уже реализовано

Проект сделан как monorepo на `pnpm`.

Основные части:

- `apps/mobile` — мобильное приложение игрока на Expo / React Native.
- `apps/dashboard` — веб-кабинет клуба на Next.js.
- `apps/api` — backend API на NestJS.
- `packages/contracts` — общие TypeScript-типы и контракты между mobile, dashboard и API.
- `docs` — документы для пилота и интеграции.
- `scripts` — вспомогательные скрипты.

### Mobile app

Уже есть:

- список клубов, карточки, экран клуба;
- выбор даты, времени, зоны и мест, проверка доступности;
- создание брони и экран успешной отправки;
- вход по телефону, dev OTP-код `0000`, хранение сессии через `expo-secure-store`;
- история броней, статусы, отмена будущей брони, logout;
- социальные экраны: сообщество, чаты, турниры, профиль;
- центр уведомлений и регистрация push-токена Expo после входа;
- нижняя навигация (`app/(tabs)`): клубы, брони, турниры, сообщество, профиль;
- рабочие фильтры и поиск в каталоге, безопасные отступы под системную
  строку и жестовую полосу Android;
- клавиатура не перекрывает поля — `react-native-keyboard-controller`
  (`KeyboardProvider` в корневом layout);
- плавные переходы между экранами и появление карточек через reanimated;
- экран клуба с разделами: живая карта зала, цены, бар, турниры, аккаунт.

### Dashboard

Уже есть:

- оформление марки Zen, как в приложении: графит, золото `#FFC83D` для действий и свободных мест,
  шрифты Unbounded (цифры, места, заголовки) и Onest (текст). Каркас — `components/app-shell.tsx`:
  меню слева на десктопе, панель снизу на телефоне, переключатель клубов;
- обзор (`/`): загрузка зала по живым сессиям, ПК, отвалившиеся во время игры, кто скоро
  освободится, заявки на бронь, выручка за сегодня рядом со вчерашней, турниры своего клуба;
- касса (`/hall`), клиенты (`/clients`), карточка клиента (`/clients/[userId]`), аналитика
  (`/analytics`) — см. разделы про клиент на ПК и CRM ниже;
- очередь заявок с подтверждением и отклонением;
- вход администратора клуба по телефону (`/login`), сессия в httpOnly-cookie;
- страница настроек клуба (`/settings`): название, адрес, город, статус, телефон, часы, теги, оборудование;
- редактор зон: добавление, удаление, цена за час и количество мест;
- fallback-данные, чтобы интерфейс не был пустым, когда API не запущен.

### API

Уже есть:

- NestJS API, health endpoint;
- клубы и зоны в PostgreSQL, каталог правится через кабинет и seed;
- проверка доступности, создание брони, получение и список броней;
- отмена брони пользователем, смена статуса администратором клуба;
- уведомление игроку при подтверждении, отклонении и завершении брони — запись в центре уведомлений плюс Expo push;
- auth по телефону, HMAC-токен с `AUTH_SECRET`, dev OTP-код `0000`;
- доставка кода: console, Mobizon или SMSC по `OTP_PROVIDER`, с ограничением частоты запросов;
- роли: `platform_admin`, `club_admin` с записью в `club_memberships`, запасной `CLUB_ADMIN_KEY`;
- PostgreSQL через `pg`, автоматическое создание таблиц при наличии `DATABASE_URL`;
- in-memory режим, если базы нет;
- защита от двойного бронирования через транзакцию и advisory lock;
- защита зоны с будущими бронями от удаления и уменьшения числа мест;
- социальные модули: чаты, профили, турниры, уведомления;
- живая карта зала `GET /clubs/:id/seatmap`: состояние каждого компьютера сейчас;
- бар клуба: `GET /clubs/:id/menu`, `POST|GET /clubs/:id/orders`;
- клубный аккаунт игрока: `GET|PATCH /clubs/:id/account`;
- турниры конкретного клуба: `GET /tournaments?clubId=...`;
- тесты: auth, clubs, club access, club hall, bookings, chat, tournaments, sessions, CRM (на PGlite).

### Права доступа

Раньше весь кабинет открывался одним общим `CLUB_ADMIN_KEY`. Теперь:

- `platform_admin` — владелец платформы: видит все клубы, выдаёт доступы;
- `club_admin` + строка в `club_memberships` — управляет только своим клубом;
- `CLUB_ADMIN_KEY` — запасной ключ уровня платформы для демонстраций. В production работает,
  только если задан явно; в dev по умолчанию `pilot-admin`.

Все административные маршруты содержат `:clubId`, и API проверяет принадлежность клуба на каждом запросе.

### Интеграции

Заготовка под провайдеров клубных систем: `manual.provider.ts` (текущий ручной режим),
`senet.provider.ts` (каркас), `club-provider.ts` (общий интерфейс).

Важно: SENET не подключён к выдуманным endpoint-ам. Для настоящей интеграции нужны официальные документы, тестовый доступ или partner/sandbox API.

## Боевой стенд на Render

- API: `https://oyna-api.onrender.com` (сервис `oyna-api`, регион Frankfurt, план free).
- Кабинет клуба: `https://oyna-cabinet.onrender.com` (сервис `oyna-cabinet`, Frankfurt, free),
  переменная `API_URL` указывает на API. `CLUB_ADMIN_KEY` там намеренно не задан:
  без него кабинет не пускает анонимного посетителя и требует вход по телефону.
- База: PostgreSQL на Neon (не на Render), `DATABASE_URL` задан в Environment сервиса `oyna-api`.
- Деплой автоматический из ветки `main` репозитория `oyna-platform`.
- Секреты (`AUTH_SECRET`, `CLUB_ADMIN_KEY`) заданы в Environment сервиса, в репозитории их нет.

Команда сборки — без `corepack`, он падает на read-only `/usr/bin/pnpm`:

```
npx --yes pnpm@11.9.0 install --frozen-lockfile && npx --yes pnpm@11.9.0 --filter @oyna/contracts build && npx --yes pnpm@11.9.0 --filter @oyna/api build
```

Права администратора клуба выдаются по номеру телефона тем же ключом:

```bash
curl -X POST -H "x-club-admin-key: <ключ>" -H 'Content-Type: application/json' \
  -d '{"phone":"+7...","name":"Администратор"}' \
  https://oyna-api.onrender.com/api/admin/clubs/vertex-arena/members
```

Каталог клубов заливается без доступа к базе:

```bash
curl -X POST -H "x-club-admin-key: <ключ>" -H 'Content-Type: application/json' \
  -d '{}' https://oyna-api.onrender.com/api/admin/catalog
```

С телом `{"catalog": [...]}` загружается свой каталог, без тела — демонстрационный.

Ограничения бесплатного плана Render: сервис засыпает
без трафика и просыпается около 30 секунд. В production код входа не возвращается в ответе
API. Пока `OTP_PROVIDER=console`, он виден только в логах Render: чтобы игрок получал
настоящую SMS, нужно задать ключи оператора и сменить `OTP_PROVIDER`.

## Сборка APK

Мобильное приложение привязано к проекту EAS `@effervescence-ss/oyna`
(projectId `18d324bc-c511-459a-b44d-80141a5adcdd` в `apps/mobile/app.json`).
Keystore создан на стороне Expo.

```bash
./scripts/build-apk.sh          # поставить сборку в очередь
./scripts/build-apk.sh --wait   # дождаться и получить ссылку на файл
```

Профиль `preview` из `apps/mobile/eas.json` собирает именно APK и подставляет
`EXPO_PUBLIC_API_URL=https://oyna-api.onrender.com/api`, поэтому установленное
приложение работает где угодно, а не только рядом с ноутбуком.

Все профили в `eas.json` закрепляют `"node": "22.14.0"`. Это обязательно:
сборщик EAS по умолчанию берёт Node 20, а pnpm 11.9 требует Node не ниже 22.13
и падает на фазе Install dependencies с `No such built-in module: node:sqlite`.

Бесплатный план Expo: 15 Android-сборок в месяц, очередь низкого приоритета,
одна сборка за раз, таймаут 45 минут.

## Клуб как отдельное место

Пилот сфокусирован на одном клубе — `zen-game-club` (Zen Game Club, 40 компьютеров,
четыре зоны, барное меню). Экран клуба в приложении собран из пяти разделов:

- **Зал** — карта всех компьютеров. Цвета с редизайна 11 октября: свободен — золотой контур,
  занят — тёмная заливка, бронь — пунктир (`colors.seat*` в `apps/mobile/src/theme.ts`).
  Те же обозначения в кассе кабинета. В августе заказчик просил «занят — зелёный, свободен —
  серый, бронь — голубая»; если это ещё актуально, менять в обоих местах. Нажатие на свободный
  компьютер открывает бронь сразу в нужной зоне.
- **Цены** — зоны с характеристиками железа и ценой за час.
- **Бар** — меню из `club_menu_items`, корзина и заказ с указанием номера
  компьютера. Сумма считается на сервере по ценам меню, а не по данным клиента.
- **Турниры** — турниры этого клуба и подача заявки. Пока клуб не создал ни
  одного турнира, раздел показывает пустое состояние.
- **Аккаунт** — клубный аккаунт игрока: свой ник, баланс, бонусы и наигранные
  часы в этом клубе. Заводится автоматически при первом открытии раздела.

Таблицы: `club_menu_items`, `club_orders`, `club_accounts`.

## Свой клиент на ПК (аналог SENET): серверная часть

Цель — не зависеть от SENET: на каждом компьютере клуба стоит клиент Zen,
время списывается с клубного баланса игрока. Сервер готов, Windows-клиента ещё нет.

- **Компьютер** (`club_stations`) привязан к месту на карте зала. Касса регистрирует его
  `POST /admin/clubs/:clubId/stations {seatId}` и один раз получает ключ; хранится только хеш.
  Потерянный ключ — `POST .../stations/:id/token`, старое подключение сразу рвётся.
- **Сессия** (`play_sessions`) идёт, пока хватает баланса (или до выбранных минут, не больше 12 ч).
  Списание при завершении поминутно, начатая минута целиком, не дольше оплаченного.
  Таймер на сервере раз в 15 с завершает истёкшие сессии.
- За компьютером одна сессия, у игрока в клубе тоже одна — это держат уникальные индексы.
- **Вход игрока**: клиент показывает 6-значный код (живёт 2 минуты), игрок вводит его
  в приложении `POST /sessions/claim {code}`. Касса может посадить игрока сама:
  `POST /admin/clubs/:clubId/sessions {seatId, phone, minutes?}`.
- **Пополнение** с кассы `POST /admin/clubs/:clubId/top-ups {phone, amount}`; идущая сессия
  сразу продлевается. Все движения баланса — в `club_balance_transactions`.
- Карта зала `GET /clubs/:id/seatmap` показывает реальную занятость и `stationOnline`.
- Канал с компьютером — socket.io, namespace `/stations`, в `auth` передаются `stationId` и `token`.
  Сервер шлёт `state` (компьютер + текущая сессия или `null`), клиент вызывает `login-code`,
  `session:end`, `heartbeat`.
- Эмулятор клиента для проверки без Windows:
  `pnpm --filter @oyna/api station -- --station <id> --token <ключ> --api http://localhost:4000`.

- **Брони и сессии**: на место, где чужая бронь уже идёт, посадить нельзя; если чужая бронь
  скоро начнётся, сессия обрезается до её начала и пополнение её не продлевает. Своя бронь
  игроку не мешает. Забронировать место, где идёт сессия, нельзя до её конца.
- **Касса в кабинете** — `/hall`: карта зала с сессиями и статусом ПК, посадка по телефону,
  завершение, пополнение, подключение компьютера с выдачей ключа.
- **В приложении** на вкладке «Зал» экрана клуба — карточка «Сесть за компьютер»: ввод кода
  с экрана ПК, остаток времени, завершение.

Не сделано: Windows-клиент (блокировка экрана, лаунчер), сканирование QR вместо ввода кода
(нужен `expo-camera` и новая сборка).

## CRM для владельца клуба

Сервис `apps/api/src/crm/`, маршруты `admin/clubs/:clubId/...` под `ClubAdminGuard`.
Работает только с базой: без `DATABASE_URL` отвечает 503 с пояснением.

- **Клиенты** (`GET clients?search=&segment=&sort=`): все, кто открыл клубный аккаунт,
  бронировал, сидел за ПК или заказывал в баре. По каждому — траты на время и бар, пополнения,
  дни визитов (всего и за 30 дней), минуты игры, брони и отмены, баланс, теги.
- **Сегменты**: VIP — топ-10 % по тратам среди тех, кто был 3+ дня, или тег VIP;
  постоянный — 4+ дня визитов за 30 дней и последний визит не старше 14 дней; новый — первый
  визит за 14 дней; спящий — 30+ дней без визитов; иначе «иногда». Флаг `atRisk` («Пропали»):
  ходил часто или VIP, но не приходит 14–60 дней — этим стоит позвонить или дать бонус.
- **Карточка** (`GET clients/:userId`): история (сессии, пополнения, корректировки, брони,
  заказы), заметки сотрудников (`club_client_notes`), теги (`club_accounts.tags`),
  корректировка баланса с обязательной причиной (`kind = 'adjustment'` в журнале).
- **Аналитика** (`GET analytics?days=7|30|90`): выручка (время + бар; пополнения отдельно,
  это деньги в кассе, а не выручка), загрузка зала от круглосуточной ёмкости, игроки
  (уникальные, новые, вернувшиеся), средняя сессия, выручка по дням, загрузка по часам недели,
  зоны, топ-10 клиентов, сравнение с прошлым периодом. Дни и часы — по времени Казахстана (UTC+5).
- В кабинете: выгрузка клиентов в CSV для Excel (`/clients/export`, точка с запятой и BOM).

SQL CRM проверяется на настоящем PostgreSQL в процессе тестов через PGlite
(`apps/api/src/database/pglite.testing.ts`). Поэтому `pnpm test` в API запускает jest
с `--experimental-vm-modules`. Помощник лежит в `src`, а не в `test/`: отдельная папка
меняла корень сборки, и API собирался в `dist/src/main.js` вместо `dist/main.js`.

## Как запустить

Понадобится:

- Node.js LTS (проверено на Node 26);
- pnpm (`npm i -g pnpm`, если его нет в PATH);
- PostgreSQL: Docker Compose (`pnpm db:up`) либо `./scripts/local-postgres.sh install` без root;
- Git;
- Expo Go на телефоне или Android emulator.

Команды:

```bash
pnpm install
cp .env.example .env
pnpm db:up
pnpm db:seed
pnpm dev:api
pnpm dev:dashboard
pnpm dev:mobile
```

Адреса по умолчанию:

- API: `http://localhost:4000/api`
- Dashboard: `http://localhost:3000`
- Mobile dev server: покажет Expo после `pnpm dev:mobile`

Для теста на реальном телефоне нужно в `.env` поставить `EXPO_PUBLIC_API_URL` на IP компьютера в локальной сети, например:

```env
EXPO_PUBLIC_API_URL=http://192.168.1.10:4000/api
```

Dev-код входа: `0000`.

## Как завести реальный клуб

1. Скопировать `apps/api/clubs/example-club.json` и заполнить данными клуба.
2. `pnpm db:seed -- --file=./clubs/<клуб>.json` — путь считается от `apps/api`.
3. `pnpm db:seed -- --club=<id> --admin-phone=+7...` — выдать администратору доступ.
4. Администратор входит в кабинет на `/login` по своему номеру и правит клуб на `/settings`.

Seed идемпотентен: повторный запуск обновляет клубы и зоны, ничего не удаляя.

## Что делать с первым клубом

Не начинать с просьбы “дайте пароль от SENET”. Правильный первый шаг:

1. Показать демо: игрок создаёт заявку, клуб подтверждает в dashboard, игрок получает уведомление.
2. Узнать, какая система у клуба: SENET, SmartShell, LANGAME или другая.
3. Собрать зоны, цены, список ПК, правила отмены, часы работы, телефон администратора.
4. Завести клуб через seed и выдать администратору доступ по его номеру.
5. Попросить только безопасный технический доступ: sandbox, partner API, тестовый аккаунт или официальную документацию.
6. Первую неделю запустить “теневой режим”: OYNA создаёт заявки, админ сверяет вручную.
7. Потом дать несколько реальных мест под бронь без онлайн-оплаты.
8. Только после стабильных броней думать об оплате, депозитах и автоматической синхронизации.
